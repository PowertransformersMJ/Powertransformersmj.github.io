## 🔧 Operaciones de Git / refactor

### L-01 · El push lo hace el director (el runtime da 403)
Los canales de push del runtime (`git push` vía proxy, `mcp__github__*`) dan **403** en este repo. **Flujo vigente (ADR-005)**: Claude commitea + deploya; **el director hace los `git push`** (GitHub Desktop o su terminal con sus credenciales). Claude NUNCA force-push a `main`. Si alguna vez se necesitara push desde el runtime, el único canal que funcionaría es `git push https://USER:TOKEN@github.com/USER/REPO.git BRANCH:BRANCH` con PAT clásico del dueño inline (el `local_proxy` resetea el remote → pasar la URL con token en CADA push). **Jamás** escribir el token a archivo/commit/PR/log; redactar con `sed 's|ghp_[A-Za-z0-9]*|ghp_****|g'`. (Full: `_legacy §0.1`.)

### L-02 · `main` solo con pedido explícito
No tocar `main` salvo orden directa del director.

### L-03 · Migrar archivo legacy SIN perder detalles visuales
Al portar un `*.html` monolítico (con JS inline) a la arquitectura moderna: comparar lado a lado contra el original en el navegador ANTES de cerrar. Para Chart.js: copiar `plugins.legend`/`plugins.tooltip` palabra por palabra y replicar el plugin `afterDraw` completo (cada `setLineDash`/`arc`/`fillText` tiene propósito de UX). 100% de paridad visual, no solo numérica. Si el director da captura del original, ESA manda. (Full: `_legacy §0.1.2.1`.)

### L-04 · Refactor 1→N NO debe vaciar la UI legacy
Al pasar de "1 entidad" a "N entidades", NO eliminar el cómputo de 1 entidad: dejarlo como **fallback** (Ruta 1 colección N≥1 → agregado; Ruta 2 colección vacía + preview legacy → cálculo con 1; Ruta 3 vacío real → placeholder INFORMATIVO con catálogo esperado, nunca stub silencioso). Verificar cada sección consumidora abriendo la página sin acciones. Síntoma del bug: director dice "eliminaste todo lo de [sección]". (Full: `_legacy §0.1.2.4`.)

## 🌐 Frontend / runtime

### L-05 · NO usar `<datalist>` para búsqueda/autocompletar
Falla en Safari (sobre todo con `autocomplete="off"`, dentro de iframe, o con extensiones de privacidad): el dropdown nunca renderiza. Patrón canónico = **combobox custom** (`<input role="combobox">` + `<ul role="listbox">`, filtro NFD case-insensitive multi-campo, ↑↓ Enter Esc, tope 30 + "… y N más", ARIA completo, `dispatchEvent(new Event('change'))` en commit para no romper handlers downstream). Ref. `initMatSelect()` en `assets/js/calculo-refrigeracion.js`. (Full: `_legacy §0.1.2.12`.)

### L-06 · Informes imprimibles: paginación manual con `.sheet` divs
Safari/WebKit **NO repite** `<thead>/<tfoot>` de tabla paginada (solo en pág 1 y última), y `position:fixed` + `@page margin` es inconsistente entre browsers. Único método universal: divs `.sheet` (8.5×11in, `page-break-after:always`) cada uno con su header/footer DOM-explícito, rellenados por un script de paginación que distribuye bloques midiendo `scrollHeight > clientHeight`. Flujo natural (sin `page-break-after:always` salvo entre documentos), `break-inside:avoid` en bloques atómicos, captura exhaustiva del formulario + totales + BOM + fórmulas con sustitución numérica + diagramas. **Verificar en Safari REAL** — `puppeteer.pdf()`/headless NO representa `window.print()`. (Full: `_legacy §0.1.2.2` y `§0.1.2.3`.)

### L-07 · Captura HD de Chart.js: escalar fontsize Y lineWidth, no solo el canvas
Si subes el canvas 4× pero dejas los font sizes en px absolutos, los textos quedan ilegibles. Escalar proporcionalmente TODOS los font sizes de las opciones, `borderWidth`/`pointRadius` de datasets, boxWidth de leyenda, y todo lo que dibuje el plugin `afterDraw` (vía `chart._exportScale`). Backup → aplicar → `resize`+`update` → capturar → restaurar. (Full: `_legacy §0.1.2.8`.)

### L-08 · Foto de referencia → embeber con `<image>`, NUNCA redibujar en SVG
Redibujar una foto del director como SVG siempre la "altera" (colores, proporciones, detalles inventados). Embeber la imagen original con `<image href>`, archivarla en `assets/img/refs/`, agregar solo anotaciones encima (cotas, regiones interactivas invisibles). SVG vectorial solo cuando NO hay foto. Si la foto es referencia, fidelidad + interactividad son obligatorias (2-3 iteraciones esperadas). (Full: `_legacy §0.1.2.10` y `§0.1.2.11`.)

## 🔥 Backend / infra / entorno

### L-09 · Deploys Firebase los ejecuta Claude (flujo ADR-005, desde 2026-06-06)
Al modificar `firestore.rules` / `firestore.indexes.json` / `storage.rules` / `functions/*`, **Claude ejecuta** `firebase deploy --only X` (firebase CLI local autenticado), **anuncia el deploy en el MISMO turno** (acción de producción) y verifica el resultado. Sin deploy: queries fallan con `permission-denied` (rules), `FAILED_PRECONDITION` (índices) o corre código viejo (functions). El **director hace los push**; Claude NUNCA force-push a `main`. (Antes era manual del director — ver ADR-005 en `99 §5`. Full histórico: `_legacy §0.1.1`.)

### L-10 · Firestore rechaza `undefined` con un `permission-denied` ENGAÑOSO
Cuando un payload tiene campos `undefined`/`NaN` (típico en objetos anidados de funciones puras), la SDK Web los enmascara como `permission-denied` aunque seas admin y las rules estén bien. Receta: helper `deepClean(payload)` (en `assets/js/data/_firestore_clean.js`) que recursivamente omite `undefined`/`NaN`/`Infinity`/funciones, preserva `null`/`0`/`''`/`false` y objetos Firestore (Timestamp/FieldValue/GeoPoint/DocumentReference). Aplicar JUSTO antes de `addDoc`/`setDoc`/`updateDoc`. (Full: `_legacy §0.1.2.6`.)

### L-11 · Re-deploy de `firestore.rules` tras CUALQUIER cambio
Si una colección NUEVA falla con `permission-denied` mientras colecciones viejas funcionan y el pre-chequeo de admin pasa → las rules en prod no incluyen el `match` nuevo (cae al `match /{document=**} { allow: if false }`). Verificar que el deploy diga "released rules ... to cloud.firestore" (no solo "deployed indexes"). (Full: `_legacy §0.1.2.7`.)

### L-12 · `/suministros/{X}` usa docId compuesto `{contrato_id}_{codigo}`
Desde la migración N5. Usar `composeDocId(cid, codigo)` de `domain/contratos.js`; nunca el código plano (falla silenciosamente para contratos post-N5). Pasar `contrato_id` en todo consumer de `/suministros`. Síntoma: "Suministro X no existe" / stock "—". (Full: `_legacy §0.1.3`.)

### L-13 · Validaciones críticas en el SUBMIT, no solo al abrir el form + doble defensa en data layer
El estado del modal NO es fuente de verdad (race conditions de queries async). Re-verificar EN VIVO justo antes de escribir; si la query de verificación falla, BLOQUEAR con mensaje accionable (no retornar `{existe:false}` silencioso). El data layer (`crear()`) revalida el invariante independientemente. (Full: `_legacy §0.1.2.9`.)

### L-14 · Lint local con `npm install` + `npm run lint:html`, NO `npx html-validate`
`npx` descarga una versión transitoria más laxa que la fijada en `package.json` → exit 0 local pero CI rojo (ej. WCAG H63 `<th>` sin `scope`). CI corre `npm ci || npm install` + `npm run lint:html`. (Full: `_legacy §0.1.2.5`.)

### L-15 · setDoc(merge:true) sobre colección con rules de enums obligatorios
El `request.resource.data` que evalúan las rules es el estado merged-post. Si el doc no existía, campos requeridos (`codigo`, `estado`) quedan `undefined` → falla la rule. Rellenar defaults seguros en el data layer respetando valores existentes. (Full: `_legacy §9.9` / v2.8.1.)

## 🔗 Integración cross-módulo (patrón canónico)

### L-16 · Integración cross-módulo = dominio puro + idempotencia + trazabilidad bidireccional
Cuando un módulo A escribe/lee datos en módulo B: (1) funciones puras en `domain/` (sin Firebase, testables); (2) data layers thin en `data/` (one-shot / realtime con debounce ~200ms / orquestador transaccional); (3) idempotencia por **marcador persistente** en el doc (no transiente); (4) trazabilidad en AMBAS direcciones (array de IDs origen→destino + identificador embebido destino→origen); (5) hook no-bloqueante (try/catch que solo loguea, **nunca re-lanza** — no revertir el write upstream); (6) tests de la función pura sin Firebase; (7) UI con 3 estados (OK/bloqueo/fuera-de-scope). (Full: `_legacy §0.1.2.13`.)

### L-17 · NO dejar pasos manuales del director post-merge para "encender" una integración
Prohibido decir "andá al admin, editá N items, confirmá X". Si la feature necesita data nueva en Firestore: auto-aplicación silenciosa idempotente al primer load, O banner accionable de UN click, O Cloud Function trigger, O script CI. Detectar el cold-start activamente (no fallar con "vacío" silencioso). El detector debe disparar si CUALQUIER atributo del mapeo congelado difiere, no solo si está totalmente ausente. (Full: `_legacy §0.1.2.14`.)

## 🛠️ Claude Code / harness (skills, config)

### L-19 · Activar una skill repo-only = copiar su `SKILL.md` a `.claude/skills/<name>/` + reiniciar
`skills/` del repo **NO es la fuente** de lo que Claude carga; el bundle `anthropic-skills:*` viene del entorno. Para activar una skill que solo existe en `skills/` (repo-only): copiar su carpeta a `.claude/skills/<name>/`, donde `<name>` = el **`name` del frontmatter** (NO el nombre de la carpeta fuente — pueden diferir, ej. `brutalist-skill` → `industrial-brutalist-ui`; sácalo con `grep -m1 '^name:' SKILL.md`). Claude Code escanea esa ruta **solo en boot** → no hay carga en caliente, **el director debe reiniciar**. Gotchas: (1) bundles con varias skills anidadas (ej. `taste-skill-main/<sub>/SKILL.md`) → copiar cada subcarpeta por separado, no la raíz; (2) carpetas que son **plugin** (`code-modernization`) o **subagente** (`code-simplifier`) NO tienen `SKILL.md` → no cargan como skill; (3) NO re-stagear skills que ya están en el bundle → colisión de `name`. Validar: `find .claude/skills -name SKILL.md` + chequear `name`+`description` en cada una. **Ojo persistencia**: `.claude/` está gitignorado (`.gitignore:22`) → lo copiado es **local-only**; si se re-clona el repo, re-correr el copy (la fuente sobrevive en `skills/`, que sí está tracked). (Ref: ADR-002, `99`.)

## 🪞 Meta: fallos del propio cerebro (Reflejo de Autocrítica `CLAUDE.md §G.4`)

> El cerebro se critica a SÍ MISMO: dónde una neurona/regla **causó un error o me

### M-01 · `brain-check.mjs` ensuciaba la raíz con un archivo `NUL` en cada corrida
**Defecto del cerebro:** el linter del template traía `git rev-parse … 2>NUL` (sintaxis de redirección de Windows). **Causa:** en macOS/Linux `2>NUL` no descarta stderr — crea un archivo literal llamado `NUL` en `cwd` cada vez que corre el chequeo de frescura 4c; el artefacto reaparecía tras borrarlo. **Corrección:** `scripts/brain-check.mjs:171` → `2>/dev/null` (2×); verificado que ya no se recrea. **Principio:** el tooling del cerebro debe ser POSIX-limpio; un linter que contamina el repo que audita es peor que no tenerlo. Si ves un `NUL` 0-byte huérfano, busca `2>NUL` en scripts.

## 🤖 IA / Claude API (Anthropic)

### L-49 · UI con requisito ambiguo o sensible → workflow de PREVIEW (dev-server + harness mock) ANTES de cablear
Síntoma/contexto (ADR-024): tras misinterpretar DOS veces un pedido de UI (gráfica "todas las pruebas en una") y no poder ejecutar la app (admin-gated + Firebase), el director pidió "implementa workflow para que sea un trabajo más preciso". **Receta**: montar un preview local y VALIDAR en el navegador antes de tocar la app. (1) **Servidor estático**: `scripts/dev-server.mjs` (Node http puro — `python -m http.server` lo BLOQUEA el sandbox del preview: `PermissionError os.getcwd()`); registrarlo en `.claude/launch.json` (`runtimeExecutable:"node"`). (2) **Harness** `_dev/preview-multiano.html` que importa los MISMOS módulos de la app + datos MOCK y renderiza el componente aislado. (3) **Claude Preview MCP**: `preview_start` → `preview_eval` (navegar/inspeccionar/clicar) → `preview_screenshot` (ver) → `preview_console_logs level:error` (errores JS). **Lo que atrapó**: la "leyenda 2019/2021/2023" del SVG NO eran chips de filtro (`document.querySelectorAll('.pe-fase-chip').length === 0`) → sin preview se habría enviado "sin filtro de año" de nuevo. Validación dura por `eval` (contar líneas SVG antes/después de un clic: 6→5 = filtra). **Cómo evitarlo**: para cualquier cambio de UI no trivial que NO puedas ver en la app real, un harness + preview + screenshot/eval es la diferencia entre "creo que funciona" y "verifiqué que funciona". Una LEYENDA no es un FILTRO hasta clicarla. El preview también sirve para confirmar el DISEÑO con el director (mock visible en el panel de preview) antes de invertir en el cableado. (Artefactos de dev viven en `_dev/` y `scripts/dev-server.mjs`; no afectan producción.)

### L-50 · Datos de prueba (mocks dev-only) NUNCA simulan otro dominio ni datos inexistentes; y blindar el límite de dominio en el código
Síntoma (ADR-027): para demostrar que el multi-año ya mostraba "todas las pruebas", inventé un bloque **DGA** (gases disueltos del aceite) con valores ficticios en el harness de preview `_dev/preview-multiano.html`. El director, que había revisado cada informe, lo cazó al instante: "¿de dónde sacas los datos de DGA? esto es **pruebas eléctricas, no análisis de aceite**". Doble error: (1) **fabricar datos** que no existen en ningún informe → simula realidad inexistente; (2) **cruzar dominios** — el DGA/análisis de aceite es físico-químico, NO una prueba eléctrica; este tablero es eléctrico. **Receta**: (a) un mock dev-only solo usa **tipos de prueba del dominio correcto** (SFRA, reactancia de dispersión, IR de núcleo, LTC/DRM, DFR son eléctricas; DGA/fisicoquímicos/furanos/humedad-papel son aceite → NO van) y sus datos ilustrativos se **rotulan como tales** ("dev-only, no de un informe real"); (b) cuando un módulo tiene una frontera de dominio, **blíndala en el código**, no solo en la convención: `familiaMA` excluye explícitamente las familias de aceite (`ES_NO_ELECTRICA`) ANTES del fallback genérico, con test que lo verifica → aunque la IA extraiga una tabla de aceite de un informe mixto, no contamina el tablero eléctrico. **Cómo evitarlo**: antes de inventar un dato de ejemplo, pregúntate si ese dato/tipo PERTENECE al dominio del módulo; verifica con el cerebro (lobe 49: el aceite tiene skill propia pero NO alimenta el tablero eléctrico). Un mock que cruza dominios no "demuestra" la feature: confunde y erosiona la confianza del director (que conoce sus informes mejor que tú). Verifica, no asumas (§3.3) también aplica a los datos de prueba.

### L-52 · Un resultado físicamente IMPLAUSIBLE = artefacto de datos, no hallazgo → RCA en el dato ANTES de mostrarlo
Síntoma (ADR-040): al añadir "tendencia de capacitancia" al panel tan δ, el workflow mostró **CHL −91.4% / CL −89.3%** vs baseline — cambios de ~10x imposibles para el mismo aislamiento. Tentación: mostrarlo como "posible desplazamiento geométrico". **Causa raíz** (verificada en los fixtures): los informes usan ESQUEMAS de medida distintos (2021 combos de 2 devanados `CH+CHL`; 2023 de 3 devanados `CH+CHL+CHT`, modos GST/UST) → la misma ETIQUETA de sección NO mide la misma capacitancia (CHL: 2233.5 pF vs 191.9 pF). **Receta**: (1) antes de mostrar una métrica derivada, pregúntate si el valor es FÍSICAMENTE plausible; si no, es artefacto → RCA en el dato (¿se comparan cosas comparables?). (2) Una métrica RATIO (tan δ, adimensional) tolera diferencias de modo/escala que una ABSOLUTA (pF, capacitancia) NO → no todas las columnas del informe son comparables entre ensayos. (3) Mejor un CAVEAT honesto ("no comparable con este dato; requiere extracción por modo") que una falsa alarma — una alarma falsa erosiona la confianza igual que un dato inventado (memoria 'no fabricar'). **Cómo evitarlo**: el workflow no solo valida que algo se VE, valida que el dato es VERDADERO; un número absurdo en el preview es una victoria del workflow, no un detalle a maquillar.

### L-54 · `reset` que REASIGNA un Set capturado por closures lo deja huérfano (filtros muertos / contador pegado) → mutar EN SITIO (`set.clear()` + re-add)
Síntoma (ADR-042): tras "Restablecer" en el panel de excitación, el contador de un filtro se quedaba pegado ("1/3") y los clicks posteriores en los chips ya no afectaban la vista. **Causa raíz**: el `reset` hacía `sel.nivel = new Set(...)` (reasignación). Pero los chips y contadores se construyen en `grupoFiltro(label, items, setSel, …)` y **capturan la REFERENCIA** del Set (`setSel`) en sus closures (`onToggle`, los `contadores.push(() => cnt.textContent = setSel.size+…)`). Al reasignar `sel.nivel` a un objeto NUEVO, los closures siguen apuntando al Set VIEJO → el filtrado real (`medsVis`, que lee `sel.nivel`) usa el nuevo, pero los chips mutan/leen el viejo: desync total. Lo destapó una feature nueva (gating de tablas) que dependía de `sel.nivel.size`. **Receta**: cuando un estado (Set/Map/array) es **capturado por closures vivos**, NO lo reasignes para "resetear" — **mútalo en sitio**: `const restore = (set, keys) => { set.clear(); keys.forEach(k => set.add(k)); }`. Misma identidad de objeto → todos los closures siguen coherentes. **Cómo evitarlo**: regla general en UI vanilla — si pasas una colección por referencia a handlers/cierres, su "reset" es `clear()`+rellenar, jamás `x = new Set()`. Si DEBES reasignar, re-cablea TODOS los closures (más frágil). Verifícalo con un ciclo en el harness: default → filtrar → reset → filtrar otra cosa, comprobando contadores Y efecto real.

### L-55 · Tabulador genérico cross-prueba: el TIPO de criterio (desbalance / valor / mínimo) decide qué columnas y colores; y el preview abre la RAÍZ por defecto
Contexto: para "ver los valores tabulados de todas las pruebas al estilo excitación" se construyó un tabulador genérico (`_dev/tablas-pruebas-preview.js`) que recorre los `bloques` de cada informe y arma, por prueba, una tarjeta banda+KPI+tabla discriminada por grupo (nivel de tensión de prueba / devanado / configuración). Tres aprendizajes reutilizables: **(1) El criterio NO es uniforme entre pruebas** → un tabulador genérico DEBE ramificar por la SEMÁNTICA del criterio, no asumir una forma: `desbalance` (excitación/relación/resistencia → columna "Desv. máx %" coloreada vs umbral), `valor` (tan δ/bujes → el VALOR ≤ umbral, sin columna de desviación), `mínimo` (aislamiento → ≥ por clase). El bug que lo destapó: tan δ mostró "Desv. máx 14.53%" en ROJO mientras el chip de criterio decía ✓ verde (el veredicto correcto es por VALOR ≤1%, no por la diferencia entre tensiones de ensayo) → contradicción visible. **Receta**: la columna/coloreado de desviación SOLO se pinta cuando `crit.kind==='desb'`. **(2) "varias series que comparten eje X" ≠ siempre "Fase A/B/C"**: bujes de dos devanados o tan δ a dos tensiones también comparten X → una heurística "comparten X ⇒ modo fases" malclasifica, y el KPI revienta al leer un campo que solo existe en el otro modo (`Cannot read 'map' of undefined`). **Receta**: extrae los valores de forma ROBUSTA en AMBOS modos (un array de números siempre presente) y calcula estado/KPI por `crit.kind`, no por el modo; el desbalance en bloques tipo-ítem (resistencia MT/BT en un mismo bloque) se calcula **por devanado** (prefijo antes de '-'), nunca cruzando devanados (MT ~160 mΩ vs BT ~19 mΩ daría un desbalance absurdo). **(3) El panel de Claude Preview abre la RAÍZ del servidor (`/`) por defecto** = `index.html` = el login (en blanco sin Firebase) → el director ve "nada". El preview vive en `/_dev/<archivo>.html`: hay que dar/abrir la **ruta completa** (mis `preview_eval` navegaban el browser automatizado, pero el panel del director seguía en `/`). **Cómo evitarlo**: al entregar un preview de una app admin-gated, di explícitamente la URL `http://localhost:<port>/_dev/...`; si el panel no navega, ofrece un índice `_dev/` enlazable. ### L-53 · Patrón de excitación 2+1: el criterio es la FORMA (externas simétricas + central distinta); la dirección HLH/LHL vs la conexión es solo INFORMATIVA (la geometría del núcleo manda)
Síntoma (ADR-041): la primera versión de `evaluarPatron` aplicaba la regla de libro "estrella ⇒ central ALTA (HLH); delta ⇒ central BAJA (LHL)" como criterio de aprobación → marcó **4/7** tríos como "irregular" en una unidad SANA (falsa alarma). **Causa raíz** (verificada con los 7 tríos reales 450108): en este núcleo de 3 columnas la **central (B) es la MENOR en estrella Y en delta** — porque la columna central tiene el **camino magnético más corto → menor reluctancia → menor corriente de excitación**, y eso lo gobierna la GEOMETRÍA del núcleo, no la conexión del devanado. La regla "delta⇒LHL" del libro no se cumple cuando la geometría domina. **Receta**: (1) el criterio de patrón 2+1 = **FORMA**: dos externas SIMÉTRICAS (Δ A–C bajo el umbral comparativo) + central como el EXTREMO distinto (la menor O la mayor, `formaOk`); la dirección esperada por conexión se calcula pero es **informativa**, no entra al veredicto (`dirCoincide`). (2) Antes de codificar una "regla de libro" como criterio duro, valida contra los datos reales de la unidad — si los contradice, es señal de que un factor más fuerte (geometría) domina; degrádala a informativa. (3) Criterio de excitación = **COMPARATIVO**, NO hay umbral % universal duro (≠ TTR 0.5%): precedencia fábrica→previos→NETA 2+1→IEEE 62/C57.152; las **pérdidas (W)** son la componente resistiva (I_exc = magnetizante + pérdidas) y también se juzgan por comparación, sin umbral propio. **Cómo evitarlo**: la teoría orienta, el dato decide (§3.3); una regla que dispara muchas alarmas en una unidad que el experto sabe sana es sospechosa de ser demasiado rígida — pídele al director el dato de fábrica como baseline real, y mientras tanto usa el informe más antiguo como proxy declarado.

### L-51 · BORRAR de más es destruir valor ajeno al pedido → ante duda de alcance, retira lo MÍNIMO señalado (no el contenedor)

Además, pregunté y ante su "lo que indico en los pantallazos" volví a escalar al máximo en vez de al mínimo. **Receta**: (1) cuando el pedido señala un ELEMENTO dentro de una vista, el objetivo es ESE elemento; un encabezado de sección visible por el scroll es contexto, no parte del pedido. ### L-35 · IA secundaria (análisis/narrativa) reusa los datos YA extraídos, NO re-manda el PDF

### L-48 · Reintento bajo presupuesto de tiempo: reserva sitio para un intento ENTERO, no solo el backoff (si no, el último reintento revienta el límite duro → 504)
Síntoma (ADR-019): tras resolver "terminated" (L-47), el reproceso del EMS denso daba `FirebaseError: deadline-exceeded` + **`504`** en la URL de la función (+ error CORS secundario — un 504 no trae cabeceras CORS, NO es un problema de CORS). Causa raíz (doble): (A) **bug del presupuesto en `conReintentosIA`**: el gate antes de reintentar solo exigía sitio para el **backoff** (~2 s), no para un **intento COMPLETO**. Con `ATTEMPT_MS` largo (12.7 min), tras abortar el 1.er intento por timeout "sobraba" para el backoff → arrancaba un **2.º intento** que corría hasta el `timeoutSeconds` (900 s) → SIGKILL de la plataforma → **504** + `deadline-exceeded` en el cliente. (B) **900 s insuficiente** para máxima calidad (`effort:high`) en un escaneo denso (>12–13 min). **Receta**: (1) el gate de reintento exige `restante > espera_backoff + intentoMaxMs + margen` (presupuesto para un intento ENTERO) → patrón "un intento largo + reintento SOLO si el 1.º falla RÁPIDO"; con sitio para un solo intento largo, nunca se arranca un 2.º que reviente el límite. (2) Dimensiona `timeoutSeconds` (y el timeout del cliente, y el watchdog) al PEOR caso real de la operación — máxima calidad sobre el documento más denso (subido a 1500 s; gen2 admite 3600). **Cómo evitarlo**: al reintentar algo CARO bajo un límite duro (Cloud Function timeout, request deadline), el presupuesto debe alcanzar para el INTENTO, no solo para esperar entre intentos; un 504/`deadline-exceeded` casi siempre es "me pasé del límite", no CORS — diagnostica por ese error, no por el CORS secundario (§3.3). El reproceso es no bloqueante (badge durable, L-45) → una espera de 12–22 min a máxima calidad es aceptable (el usuario navega y vuelve), pero el límite debe cubrirla.

### L-47 · "Claude API: terminated" = bodyTimeout de undici (~5 min) corta el stream largo → extender el bodyTimeout del TRANSPORTE, no el timeout del SDK
Síntoma (ADR-018): "Reprocesar" un informe denso fallaba con `500` + `FirebaseError: Claude API: terminated` (visible recién cuando el director compartió la CONSOLA del navegador). Causa raíz: `terminated` es de **undici** (cliente HTTP de Node tras `fetch` global, que usa el SDK de Anthropic). undici aplica un **`bodyTimeout`/`headersTimeout` por defecto ~300 s (5 min)** de inactividad del stream. La extracción densa (Opus + `thinking` + `effort:high` + 32k) tarda **> 5 min** → undici corta → `TypeError: terminated` (cause `UND_ERR_BODY_TIMEOUT`). **Trampa**: el `timeout` del SDK de Anthropic (10 min por defecto) es OTRA capa — NO cambia el `bodyTimeout` de undici; subir el del SDK no resuelve "terminated". **Receta**: pasar al cliente un **dispatcher de undici sin bodyTimeout** → `new Anthropic({ …, fetchOptions: { dispatcher: new Agent({ bodyTimeout: 0, headersTimeout: 0, keepAliveTimeout: 60000 }) } })` (dependencia `undici@^6`; Node's global `fetch` respeta `init.dispatcher`). Así el stream tarda lo que necesite; el límite real lo ponen el timeout por-intento (`conTimeoutAbortable`, L-46) + el `timeoutSeconds` de la función. Además: clasificar `terminated`/`UND_ERR_*`/`other side closed`/`premature`/`socket` como TRANSITORIO (mirar también `e.cause.code/message`) para que reintente. **Cómo evitarlo**: (1) el `timeout` de un SDK HTTP y el `bodyTimeout` del transporte son capas DISTINTAS — para streams largos extiende el del TRANSPORTE; (2) NO bajar `effort`/modelo (degradaría la extracción, L-24/L-26) cuando el problema es de transporte; (3) diagnostica por el MENSAJE de error REAL (la consola del navegador trae el `code`/`message` de la CF, §3.3) antes de tocar el modelo — "mil intentos" sin ver el error concreto es adivinar.

### L-46 · `await` desnudo sobre un stream de IA = cuelgue invisible e infinito → timeout INTERNO que ABORTA + watchdog (el estado terminal debe estar GARANTIZADO)
Síntoma (ADR-017, tras 3 intentos fallidos en sesiones distintas): "Reprocesar" mostraba "⟳ reprocesando…" y **nunca** pasaba a procesado/error — colgado para siempre; "llevamos mucho tiempo con lo mismo". Causa raíz VERIFICADA en código: `conReintentosIA` hacía `return await fabricar(i)` (la llamada `client.messages.stream(...).finalMessage()`) **SIN timeout por intento**; el presupuesto `deadlineMs` solo se revisa en el `catch`, o sea DESPUÉS de que un intento FALLA. Si el stream de Claude **se cuelga** (ni responde ni falla — frecuente bajo "overloaded", peor con `thinking`+`effort:high`), el `await` no retorna nunca → la Cloud Function corre hasta el **SIGKILL de plataforma (timeout 900 s)** → **ningún `catch`/`finally` corre** → el `marcarReproceso('error')` jamás se ejecuta → el estado queda `'en_curso'` para siempre. **Por qué los fixes previos NO bastaron**: el reintento (L-44) solo se dispara tras un FALLO — un cuelgue no "falla"; subir el timeout solo ALARGA la espera colgada; el estado durable (L-45) muestra el estado pero el estado NO AVANZA. Pista forense: en `firebase functions:log`, líneas de error **VACÍAS** = kill abrupto de plataforma (OOM/timeout), no una excepción capturada. **Receta**: (1) **timeout INTERNO por intento con AbortController** — `conTimeoutAbortable(fabricarConSignal, ms)` pasa el `signal` a `client.messages.stream(params, {signal})`, hace `Promise.race([finalMessage, timer])`, y al vencer **ABORTA el signal** (cancela el stream colgado) + rechaza `TimeoutIA` (transitorio → reintentable). Así la promesa SIEMPRE se asienta; jamás se llega al SIGKILL. (2) **Presupuesto total < timeout de plataforma** (aquí 2×400 s + persistencia < 900 s). (3) **Watchdog global** (`setTimeout` ~870 s que escribe `'error'` si la función sigue viva, cancelado en cada salida) por si se cuelga algo más (Storage/Firestore). (4) **Memoria con margen** (1→2 GiB): un OOM-kill TAMPOCO corre `catch` → también dejaría el estado colgado. **Cómo evitarlo**: NUNCA un `await` desnudo sobre una operación de red que pueda colgarse (un stream de IA es el caso típico) — acótalo con un timeout que ABORTE el recurso. En una Cloud Function, el estado terminal de un trabajo NO puede depender solo del camino feliz ni del `catch` (un kill no los corre): debe estar GARANTIZADO por timeout-por-operación + watchdog. Distinguir "lento" de "colgado": el timeout interno debe ser ≥ el peor caso legítimo (aquí 2–5 min → 6.7 min) para no abortar extracciones válidas.

### L-45 · Operación larga (IA/red) = trabajo asíncrono OBSERVABLE: el servidor persiste + estado durable; la UI dispara y observa
Síntoma/contexto (ADR-016): tras añadir reintento (L-44), el director seguía reportando "transcurre el tiempo y no se aprecia si terminó o hubo problemas" al "Reprocesar". Causa raíz: el reproceso era una llamada BLOQUEANTE de varios minutos cuyo feedback era un `setInterval` que corría **independiente del estado real del servidor** (no distinguía "trabajando" de "colgado"), con persistencia en el NAVEGADOR *después* de responder → si el cliente se desconectaba/recargaba/agotaba el tiempo, el trabajo se perdía y el motivo de error vivía solo en un toast efímero. Más reintento/timeout solo ALARGA la espera opaca; no la resuelve. **Receta (ADR-016)**: modelar la op larga como **trabajo asíncrono observable**: (1) la **Cloud Function PERSISTE** el resultado ella misma (admin SDK) reusando los MISMOS sanitizadores del dominio que el cliente (sincronizados a `functions/domain` por el predeploy → una sola fuente de verdad, sin divergencia, L-36); (2) escribe un **ESTADO DURABLE** en el doc (`reproceso:{estado:'en_curso'|'ok'|'error', inicio|fin, motivo}`) en CADA camino (arranque + éxito + cada fallo); (3) la **UI solo dispara y observa** (onSnapshot) → badge terminal claro ("⟳ reprocesando… desde HH:MM" → "procesado"/"⚠ falló: motivo"), **sobrevive a recargas**, no bloquea, con **guard de stale** (`en_curso` > tope de la CF → "interrumpido", reintentable); el botón se gatea por el estado durable, no por DOM. Escopar el modo: un flag/`informeId` distingue "persiste server-side" (reproceso) de "devuelve crudo" (carga, que tiene su propio upsert/confirm) — sin tocar el camino existente. **Cómo evitarlo**: nunca un contador de UI desacoplado del estado real para una op de minutos; nunca persistencia solo-cliente para algo que debe sobrevivir a una recarga; el estado y el motivo de fallo van a la base, no a un toast. Para mover lógica de persistencia al servidor, REUSA el dominio (no re-implementes la sanitización). Helpers puros que el servidor necesita → muévelos a `domain/` con re-export back-compat (`deepClean`, `derivarBushing`).

### L-44 · Llamada a IA/red = reintento con backoff + presupuesto de tiempo; transitorio se absorbe, permanente se relanza
Síntoma/contexto (ADR-015, TODO-09): "Reprocesar" un informe falló con un 500 puntual aunque el PDF era legible y el informe perfecto — la CF dio `HttpsError('internal')` y el usuario tuvo que reintentar a mano. Causa raíz: `client.messages.stream(...).finalMessage()` envuelto en un único `try/catch` SIN reintento → cualquier fallo TRANSITORIO de la API de Claude (429 rate-limit, 500, 502/503/504, **529 overloaded**, corte de stream) o que el modelo NO llamara la herramienta (hipo de "conformismo", L-26) se surfaceaba como fallo duro. Esos hipos son culpa de la IA/infra, no del usuario. **Receta (`functions/reintentos.mjs`, módulo PURO testeable sin Firebase)**: (1) **clasificar** el error — `esErrorTransitorioIA` mira `status` (408/409/425/429/5xx/529), `name` (`APIConnectionError/Timeout`) y patrones (`overloaded/ECONNRESET/socket hang up/…`); permanente/externo (401 auth, 400 invalid_request, 413 payload) → relanzar de inmediato (no insistir sobre un error real). (2) **backoff exponencial + jitter**, respetando `Retry-After` si vino, con tope. (3) **`conReintentosIA(fabricar, {intentos, deadlineMs})`**: reintenta SOLO transitorios; `fabricar` DEBE devolver una promesa NUEVA por intento (un stream consumido no se reusa); **presupuesto de tiempo** (`deadlineMs`) que NO inicia un intento sin margen → nunca excede el `timeoutSeconds` de la CF. (4) **"sin tool_use" se marca 529** (transitorio) para que el reintento lo absorba. (5) cliente Anthropic con `maxRetries:0` → el reintento lo gobierna el helper, no el backoff opaco del SDK (que no cubre mid-stream ni "no tool block"). (6) presupuesto coherente cliente↔servidor: `timeoutSeconds` 540→900 + `httpsCallable` timeout 540000→900000 + `conTiempoLimite` del reproceso. **Cómo evitarlo**: toda llamada a IA/red propensa a transitorios va envuelta en reintento con backoff + presupuesto; clasifica (transitorio↔permanente) en vez de tragar/insistir a ciegas (§3.3); el usuario solo ve un fallo cuando la causa es ajena a la IA y al código (sin saldo, PDF ilegible, infra caída) — con mensaje claro y reintentable a mano.

### L-43 · No re-correr la IA (cara/lenta) para BACKFILL de campos derivables — usar el diagnóstico ya guardado

### L-25 · Purgar archivos sensibles del historial git (filter-repo)

2. Registrar los SHAs actuales de las ramas afectadas (`git branch -a --contains <commit-que-lo-añadió>`) para rollback.

### L-30 · Firestore NO admite arrays anidados → serializar payloads complejos a string JSON
Síntoma: al mover los bloques a Firestore (L-29), `setDoc()` falló con `Function setDoc() called with invalid data. Caso real: ADR-007, `guardarBloques` guarda `payload` string. **Cómo evitarlo**: antes de `setDoc` de datos derivados de un LLM o de tablas, asumir arrays anidados → string JSON por defecto.

### L-32 · Cambiar el prompt ≠ que el LLM obedezca → VERIFICAR la salida cruda antes de declarar hecho
Síntoma: reforcé el prompt para que la IA emitiera la `tabla` de detalle COMPLETA en las curvas por TAP (excitación/relación/resistencia), declaré la feature lista y la desplegué; al revisar el tablero, las tablas seguían flacas (TAP|A|B|C). Causa raíz: la IA puso los datos en `series` (la curva) y **omitió `tabla`** pese a la instrucción — el render cayó a la tabla derivada de las series. Una instrucción en prosa ("incluye la tabla completa") es una sugerencia DÉBIL: el LLM la ignora si ya cubrió el dato de otra forma. Repetí el anti-patrón §3.3 (afirmar sin evidencia) al asumir que cambiar el prompt = obtener el resultado. **Receta**: (1) tras tocar un prompt, VERIFICA la salida real en una corrida (logs `[IA-DIAG]` con `mediciones_raw`/`bloques_raw`, o el panel "Interpretación cruda") ANTES de decir "hecho"; el `[IA-DIAG-RESUMEN]` trae `n_bloques`/`n_series` pero NO si la `tabla` vino — hay que mirar el crudo. (2) Para forzar FORMATO/estructura, un **ejemplo few-shot concreto** en el prompt es mucho más fuerte que prosa imperativa. (3) Si la fiabilidad sigue baja, considera marcar el campo `required` en el tool schema o derivar el dato en el cliente. Caso real: ADR-008 lote 4→5, `functions/index.js` SYSTEM_PRUEBAS_IA. **Cómo evitarlo**: nunca cerrar una tarea que depende de la salida del LLM sin haber leído esa salida en una corrida real.

### L-33 · El LLM omite estructura REDUNDANTE → derivar en el cliente + adjuntar lo único-del-PDF inline
Síntoma: tras L-32, ni siquiera el ejemplo few-shot logró que la IA emitiera la `tabla` ancha de 17 filas en las curvas por TAP (verificado por logs: `tabla cols=0` en excitación/relación/resistencia, 2 corridas). Causa raíz: pedir una `tabla` que RE-EMITE datos que el LLM ya puso en `series` (TAP + valor por fase) es trabajo redundante y voluminoso → el modelo lo evita sistemáticamente, da igual cuánto insistas. **Receta (la que funcionó, ADR-008 lote 6)**: NO depender del LLM para lo que se puede construir o derivar:
- **Derivar en el cliente** lo computable a partir de lo que el LLM SÍ emite fiable (las `series`): columnas Desviación %/Evaluación con `derivarTablaTAP()` (dominio puro, testeable). Estas aparecen sin re-extract, solo con desplegar el frontend.
- **Canal `extra` por punto** para lo único-del-PDF (Potencia W, tensión, relación teórica, %DIF, R.Ref): el LLM lo adjunta INLINE al punto que YA está emitiendo (`{x,y,extra:{...}}`) — mínima data nueva, sin re-emitir índices ni primarios → mucho más fiable que una estructura paralela.
- **Umbrales/criterios normativos = DOMINIO, no LLM**: `UMBRAL_DESBALANCE`/`CRITERIOS_NORMA` los adjunta el shell; nunca confiar en que la IA los traiga.
**Cómo evitarlo**: cuando una salida del LLM falle 2 veces, no insistas en el prompt — re-arquitectura: ¿qué es derivable de lo fiable? ¿cuál es el mínimo dato nuevo que el modelo sí dará inline? El prompt es la última palanca, no la primera.

### L-34 · Auto-graficar TODA magnitud derivada produce ruido/duplicados → curar qué amerita gráfica
Síntoma: al graficar automáticamente cada clave `extra`/derivada de un bloque, el tablero se llenó de gráficas redundantes — R.Ref ≈ R.Medida (curva IDÉNTICA a la principal), %DIF duplicaba la gráfica de desviación, Tensión/Relación teórica son entradas monótonas sin valor diagnóstico. Causa raíz: "renderiza todo lo que tengas" trata datos de TABLA como datos de GRÁFICA. **Receta (ADR-009, `bloquesDeExtra`/`EXTRA_GRAFICABLE`)**: la data secundaria va a la TABLA por defecto; SOLO se grafica una magnitud DISTINTA y diagnóstica (en pruebas: la Potencia, su propia escala). Curar con un criterio (regex/allowlist/flag) qué amerita su propia gráfica; el resto, tabla. **Cómo evitarlo**: al auto-renderizar desde datos, distingue "MOSTRAR el dato" (tabla) de "VISUALIZAR una tendencia/relación" (gráfica) — no son lo mismo; más gráficas ≠ más claridad.

### L-31 · Las claves categóricas que emite el LLM NO son estables → aliasear, no igualar
Síntoma: tras un cambio de prompt, el scorecard dejó de mostrar la fila "Tan δ de devanados" — la IA empezó a emitir `prueba: "tan_delta"` cuando antes emitía `"tand"`, y el código filtraba con igualdad exacta (`keys.includes('tand')`). Causa raíz: el valor de un campo de **clasificación libre** que produce el LLM (familia de prueba, categoría, etiqueta) puede variar entre corridas/versiones de modelo/prompt aunque el dato sea el mismo. Igualar contra UN string es frágil. **Receta**: cualquier MATCHING contra una clave categórica del LLM debe usar un **conjunto de alias** (`['tand','tan_delta']`) o normalizar (lowercase + sinónimos) antes de comparar. Lo mismo aplica a `prueba`, `tipo_prueba`, nombres de sección, unidades, etc. Caso real: ADR-008, `FAMILIAS_SCORE` aliasea `tand`/`tan_delta`; `bloqueDesviacion` keya por `prueba==='excitacion'` (vigilar si cambia). **Cómo evitarlo**: nunca asumir que el LLM repetirá literal una clave categórica; diseñar el consumo con alias/normalización desde el inicio.

### L-57 · "Hazlo como X" → encuentra QUÉ componente produce X antes de construir uno nuevo
Síntoma (ADR-050): el director pidió "las tablas de tan δ como en corriente de excitación". Asumí que las tablas de excitación salían de su panel (`excitacion-panel.js`) y recreé un panel tabular dentro de `tand-panel.js`. El director lo rechazó: "no se aprecian como excitación". Causa raíz: NO verifiqué de dónde salen REALMENTE las tablas de excitación — las renderiza `montarPanelPrueba(host,'excitacion',…)` (`tablas-pruebas-panel.js`), un componente compartido que **ya soportaba `'tand'`** (en `ORDEN`/`NOMBRE`/`NORMA`/`CRIT`). Construí desde cero algo que ya existía y se invocaba con un string distinto. **Receta**: ante "hazlo como X", PRIMERO localiza el código que produce X (grep del render real, no del panel "obvio") y comprueba si ya es reutilizable para tu caso — casi siempre lo es. Revertí a HEAD y reusé el componente: idéntico al instante. **Cómo evitarlo**: "parecerse a X" = "usar el mismo componente que X", no "reimplementar algo que se le parezca". Verifica el origen real (§3.3) antes de escribir una línea.

### L-58 · Veredicto multi-norma: un chip POR NORMA, nunca un estado consolidado para todos
Síntoma (ADR-050): el director vio un tan δ de **0.51%** marcado ✕ en NETA **y** en IEEE ("¿por qué no cumple si está dentro de los parámetros?"). 0.51% SÍ cumple IEEE (≤1%); solo supera la guía NETA (0.5% → investigar). Causa raíz: `chipsCriterio(familia, estado)` recibía UN estado consolidado (el peor) y lo aplicaba a TODOS los chips → ambas normas se pintaban igual, contradiciendo la doctrina multi-norma (L-36/L-37) y al propio `bloqueDiagnostico` de abajo que sí evalúa por norma. **Receta**: todo chip/badge por norma debe salir de `evaluarMultiNorma(familia, metrica).opticas[i].estado` (cada óptica su nivel), mapeando nivel→símbolo (0 ✓ cumple · 1-2 ⚠ investigar/vigilar · ≥3 ✕ fuera de norma); si una óptica es informativa (nivel <0, sin % duro) cae al consolidado. **Cómo evitarlo**: el consolidado conservador es para el VEREDICTO GLOBAL, nunca para pintar cada norma; "investigar" (naranja) ≠ "no cumple" (rojo) — no colapses niveles ni normas. Verifica que los chips COINCIDAN con la tabla de diagnóstico (si divergen, hay bug).
