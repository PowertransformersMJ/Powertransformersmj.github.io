## 3. Reglas permanentes nuevas

### §0.1.2.10 (commit `110404e`)

**Render visual con foto de referencia · fidelidad +
interactividad obligatorias.**

5 puntos:
1. Si el director comparte foto, la foto MANDA. No inventes
   posiciones — pregunta si dudas.
2. Detalles 3D NO son opcionales (gradientes, sombras, capas
   apiladas, highlights, detalles funcionales reales).
3. Render de entidades seleccionables DEBE ser interactivo
   (click → modal con controles, no dropdowns externos).
4. Verificación visual obligatoria antes de cerrar el commit.
5. Esperar 2-3 iteraciones con el director — fidelidad rara
   vez se logra en un solo intento.

### §0.1.2.11 (commit `75d1d13`)

**Foto de referencia → embeber con `<image>`, NUNCA redibujar
en SVG.**

7 puntos:
1. NO redibujar en SVG · siempre será aproximación.
2. Embeber con `<image href="...">` dentro del SVG.
3. Archivar imagen en `assets/img/refs/<desc>.png`.
4. Para ajustar tamaño usar `preserveAspectRatio="xMidYMid meet"`.
5. Solo agregar encima: título, cotas, regiones interactivas
   invisibles para clicks. Nada que altere la apariencia.
6. Anti-patrones a evitar: "redibujar mejor con gradientes
   futuristas", "mi versión que respete el espíritu", "animar
   partes vectorialmente sin OK".
7. Excepción legítima: SVG vectorial sí va cuando NO hay foto
   provista (cálculos, gráficos Chart.js, diagramas de bloques).

## 10. CI · concurrency cancel (anotación operativa)

Al cierre de la sesión, después del último push (`31fa320` ·
docs), GitHub mostró en la PR:

```
1 cancelled, 1 successful checks
✗ CI · Lint estático / Lint HTML (push) · Cancelled after 15m
✓ CI · Lint estático / Lint HTML (pull_request) · Successful in 11s
```

**Esto NO es un fallo real.** Es comportamiento configurado en
`.github/workflows/ci.yml`:

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Cuando se hace un push nuevo (`31fa320`) sobre el mismo branch
ref, GitHub Actions cancela automáticamente cualquier run en
vuelo del push anterior (`75d1d13`). El "Cancelled after 15m"
es solo el wallclock desde que se encolaron — no significa que
ese run se haya colgado.

El check que GitHub usa como gate del merge es el `pull_request`
job, que se ejecuta sobre el ref de la PR (no del push directo
al branch). Ese ran clean en 11s sobre el commit más reciente.

**Cuando aparezca este patrón:**
- ¿`pull_request` está verde? → mergear sin problema.
- ¿`pull_request` también falla? → ahí sí hay un bug real.
- ¿Quieres ver el `push` check verde por estética? → re-run
  el job desde la UI de Actions (botón "Re-run jobs").

NO retentar el push esperando que el check verde · solo
re-run o mergear.
